# Changelog

## Unreleased

### Fixed

- `delete-deployment` no longer reports `Deployment <id> deleted successfully.` for a deletion that has only been queued. `DELETE /deployment/api/deployments/{id}` answers `200` with the `Deployment.Delete` request it created — `status: PENDING`, observed on vRA 8.18 — and the deployment then reads `DELETE_INPROGRESS` for about 45 s before it answers `404`; the client discarded that body and the tool declared the deletion done, so an agent that trusted the line and moved on could still find the deployment, and its resources, present. `VroClient.deleteDeployment` now returns the `DeploymentRequest` the service answers with — an empty body reads as `{}`, and a bare-array body, the shape the sibling catalog route serves, is unwrapped to its first element rather than cast whole — and the tool reports the deletion as *requested*, prints the request ID and status when they are served, and names `get-deployment` (poll to `404`) and `list-deployments` (poll to absence) as the way to confirm it. The `run-deployment-action` success text likewise gains a next step chosen from the action and the request's status rather than a fixed sentence: a power action is not tracked by `get-deployment` (a deployment read `CREATE_SUCCESSFUL` throughout a `PowerOff` and a `PowerOn`), a `Deployment.Delete` is (poll to `404`), and a request that is not in a running state — an approval hold, a failure — is reported as held or finished instead of as something to wait for. Both tools render the request through one shared set of lines. Reading a request back by ID is tracked as VCFO-094 (#212). Source-breaking only for a TypeScript consumer of `deleteDeployment`'s return type, which was `Promise<void>` (VCFO-088).

- `create-deployment` reports the deployment ID and name it just requested. `POST /catalog/api/items/{id}/request` answers a **bare array** of `{deploymentId, deploymentName}` on VCF Automation 9.1 — not a `Deployment`, and carrying neither `id`, `name` nor `status` — but the client typed the response as a single `Deployment` and read those three fields off it, so every one was `undefined` and the tool printed a bare `Deployment request submitted.` with nothing to act on. The caller had to recover the identifier from `list-deployments` by name, which is ambiguous the moment two deployments share one, and silently so: nothing in the output said an identifier had been expected. `normalizeCatalogItemRequest` now accepts the array arm and the single-object arm, and the `deploymentId`/`deploymentName` spelling as well as `id`/`name`, so a platform answering either shape still yields identifiers; a response that genuinely carries none now says so and names `list-deployments` with the project ID rather than staying silent. The success line also states that provisioning is asynchronous, which is what makes the returned ID immediately useful. Found and verified on a 9.1 tenant session, where the shape had never been observed before (VCFO-074).

- `expectedProjectName` no longer refuses every call on `delete-deployment` and `run-deployment-action`. Both compared the expected value straight against `deployment.projectName`, and a VCF Automation 9.1 deployment carries `projectId` but **no `projectName`** — so the guard reported `project name: expected "…", found (missing)` and refused every legitimate call, making the argument impossible to use rather than merely unverified. This is the VCFO-077 defect class reintroduced through a field that was assumed rather than observed, which is why the fix keeps the same resolution: the name is taken from the deployment when a platform does serve it, and otherwise resolved through the project service using the deployment's own `projectId` — the way `guardCreateDeploymentTarget` already resolved it for `create-deployment`. The argument now *works* rather than failing politely, the extra read fires only when `expectedProjectName` is supplied, and a project that genuinely reports no name is reported as "cannot verify" rather than as a mismatch, still refusing so a caller who asked for verification is never told a target was confirmed when it was not. Verified live: a delete carrying `expectedProjectName` now succeeds, which was impossible before (VCFO-074).

- `get-deployment` resolves the project name instead of printing an opaque ID. Its `if (deployment.projectName)` branch never fired on VCF Automation 9.1, which serves a deployment's `projectId` but no `projectName` (VCFO-074), so every real call fell through to `Project ID:` alone and the name the renderer intended to show was unreachable through the tool — the VCFO-077 class again, in a read rather than a guard. The name is now resolved through the project service by the same `resolveDeploymentProjectName` the write guards already used, and both lines print when both are known, since the ID is what the other deployment tools take as an argument. The read is unconditional here, unlike the guards' — describing the deployment is this tool's whole job, where there the read exists only to serve a guard the caller opted into — and a project read that fails degrades to the ID alone rather than failing the call, so losing the enrichment never loses the deployment. `list-deployments` keeps the unresolved fallback deliberately: there the same resolution would cost one extra read per row (VCFO-091).

- The `vcfa://actions/{id}` resource no longer serves an action's script. `get-action` returns only a sha256/length summary of `action.script` unless the caller passes `includeScript: true` — a flag whose own description says the script "may embed credentials" — but the resource serialized the record verbatim, so the gate was one URI read away from being sidestepped by a caller who never asked for the script at all. The resource now serves the same `{ included: false, sha256, length }` shape the context snapshot has always written, and the digest is taken over the same bytes the tool hashes, so a caller can compare a resource read against a tool result and get the same value; a test asserts that equality so the two cannot drift. The full script is still one `get-action(includeScript: true)` call away. Filed separately as the resource-layer half of the never-print-secrets rule after VCFO-091 fixed the deployment case (VCFO-092).

- A `SecureString` workflow execution output is no longer printed in cleartext. `run-workflow-and-wait` and `get-workflow-execution` rendered every output parameter through `formatVroValue`, which unwraps the envelope and prints it and by design withholds nothing, while `get-configuration` reached that same renderer only behind an `isSecureAttributeValue` guard — so the identical declared type read `[redacted]` as a configuration attribute and cleartext as an execution output. `formatVroValue`'s own doc comment claimed the two surfaces were shared "so the two cannot drift apart", and the sharing had kept the formatting aligned while the guard lived at one call site of three. Both execution paths now go through a new `formatVroValueRedacted` that applies the same detection, unduplicated: the declared type, and the type key vRO wrapped the value in. Both arms matter, because no lab has run a workflow with a secure output and the shape vRO serves is unobserved. This is the surface where the guard is load-bearing rather than defensive — vRO does not return a `SecureString` attribute value at all, but an execution output is a value the engine just produced and does return. A test drives `get-workflow-execution` and `get-configuration` off one client and one secret so the two cannot drift again. Left deliberately unfiltered: execution log lines and a failed execution's exception text, which carry no type and are served verbatim, and a secret nested inside an untyped composite output — each now stated in the tool description and the docs rather than silently assumed (VCFO-093).

### Changed

- **`VCFA_TARGET_PLATFORM=vra8` now sends catalog-service and deployment-service writes**, so `create-deployment`, `delete-deployment` and `run-deployment-action` work on vRA 8 instead of returning the `pending lab verification` refusal. Both guards were lifted on evidence, per service and independently: a vRA 8.18 lab that had gained one released catalog item was driven through the real tool handlers, and a disposable deployment was requested (both `expected*` target guards refusing a mismatch first), polled to `CREATE_SUCCESSFUL`, powered off and on through `run-deployment-action` with every guard supplied, and deleted through `delete-deployment` with all four, polled to `404`, with the environment back at its starting count. A raw-HTTP pass recorded the wire shapes beforehand: the catalog request answers a bare array of `{deploymentId, deploymentName}` and the action list a bare array of six-key objects, both exactly as VCF Automation 9.1 does, and a day-2 submission answers a `DeploymentRequest` (`PENDING`/`INITIALIZATION` → `INPROGRESS` → `SUCCESSFUL`) — a vRA 8.18 observation only, since no 9.1 round has submitted an action. The refusal for project-service writes and the fail-closed default for an unrecognized service are unchanged; `export-configuration-file` stays refused in this mode for its own, unrelated reason. This is the first day-2 action submitted on any platform, so the `DeploymentRequest` type now carries what the wire served, all optional, including `cancelable` and `approvedAt` (VCFO-088).

- `VroClient.createDeploymentFromCatalogItem` returns `Promise<CatalogItemRequestResponse>` instead of `Promise<Deployment>`. The old signature was not a narrowing of the truth but a description of a response that does not exist: the route answers a bare array of `{deploymentId, deploymentName}`, so the `Deployment` that callers were handed had `id`, `name` and `status` all `undefined` at runtime while type-checking as present. Source-breaking for a TypeScript consumer importing the client directly — `(await client.createDeploymentFromCatalogItem(...)).id` compiled before and no longer does — but it breaks at compile time exactly where it was already broken at runtime, and `normalizeCatalogItemRequest` in `src/tools/deployment-tools.ts` is the supported way to read identifiers out of either response arm. No MCP tool contract changes (VCFO-074).

- `vcfa://` live-object resources now mirror what their matching `get-*` tool withholds, and say so in their own MCP description. Beyond the action script above, `vcfa://subscriptions/{id}` summarizes `constraints` the way `get-subscription`'s `includeConstraints` gate does, and `vcfa://configurations/{id}` withholds an attribute value the server declares secure — by declared type and by the value envelope vRO wrapped it in, matching `get-configuration` rather than the stricter context snapshot, which blanks every attribute value regardless of type. **This changes the JSON these three resources serve**, so a consumer parsing `script` or `constraints` as a string now receives an object. The contract is deliberately about withholding rather than field-set parity: `vcfa://workflows/{id}`, `vcfa://resource-elements/{id}` and `vcfa://packages/{name}` are unchanged and documented as such, because their tools withhold nothing — a package's content listings are omitted by `get-package` for brevity, and brevity is not secrecy. The four projections live in `src/resource-views.ts`, and `contentMetadata` moved to `src/content-metadata.ts` so the resource and snapshot surfaces share one shape instead of three copies. A workflow definition parameter is deliberately left alone: `VroParameter.value` exists only because that type is shared with execution outputs, and no platform has been observed serving a value there. Note the related tool-layer gap this did not touch — a `SecureString` workflow **execution output** still prints in plaintext (#208, VCFO-093) (VCFO-092).

- **`run-workflow-and-wait` and `get-workflow-execution` print less than they did.** An output parameter whose declared type or value envelope reads secure or encrypted now renders `[redacted]` instead of its value, so a caller reading such an output today stops seeing it — deliberately, and with no flag to turn it back on: this repo gates bulky content behind a flag (`includeScript`, `includeContent`) and does not gate secrecy. A plain output is untouched, including an `Array/string` and an empty string. `get-workflow-execution-logs` is unchanged and still serves log bodies verbatim, which its description now says (VCFO-093).

### Added

- `get-catalog-item` renders the item's request schema as the input contract for `create-deployment`. VCF Automation 9.1 serves `schema.properties` and `schema.required` on a catalog item — the names, types, and constraints of the inputs a deployment request must carry — and the tool rendered neither, so an agent driving a deployment through the MCP surface had no way to discover them and had to guess, which is exactly what the project's "do not invent environment-specific values" rule forbids. Each input is listed with its type, whether it is required, its title or description, and its `pattern` or `enum` where present. A property marked `encrypted: true` is listed and flagged but its stored `default` is **never** printed: a default on an encrypted input is a credential, and printing it would breach the never-print-secrets rule. The item's `isRequestable` is rendered too, since an item that cannot be requested is worth knowing about before composing a request (VCFO-074).

- `get-deployment` renders the inputs the deployment was requested with. `GET /deployment/api/deployments/{id}` serves an `inputs` object keyed by input name and `Deployment.inputs` has modelled it since VCFO-074, but nothing read it, so an agent asked to reproduce, compare or troubleshoot a deployment could not answer what it had actually been given — the same gap PR #204 closed one step earlier in the lifecycle, where `get-catalog-item` serves what an item *takes* and this serves what a deployment *was given*. It is not cosmetic: two deployments of one catalog item were observed on 9.1 carrying different input sets because they were requested against different released blueprint versions, which is also why the blueprint behind the requested catalog item version is now rendered alongside. Values render as JSON so they can be replayed into `create-deployment`'s `inputs`, the opposite of the configuration-attribute rendering where the quotes are an artifact (VCFO-080). **An input whose name reads as credential material is withheld as `[redacted]`, at any depth inside an object or array value**, and the header then says those values must be supplied fresh. A deployment record carries no marker saying which of its inputs were encrypted, and the catalog item's schema cannot supply one — it can only be read at its current version, not necessarily the `catalogItemVersion` the deployment was requested against, which is the very drift above — so the key's own name is the only signal available, exactly as it already was for project custom properties. The heuristic is not a guarantee and the tool description and docs both say so. The same redaction now applies to the `vcfa://deployments/{id}` resource, which serialized the record verbatim (VCFO-091).

## 3.2.0 - 2026-09-15

The first release since 3.1.0. The default `vcfa` platform now has the per-tool verification record that
only the non-default `vra8` mode had: all 78 registered tools driven against VCF Automation 9.1 in a single
204-call sweep that returned the environment to its exact starting counts, recorded in
`docs/operations/vcfa-verification-matrix.md`. Measuring rather than inheriting corrected three things the
server had been getting wrong — a `403` there is a denial rather than a stale session, so it no longer costs
a pointless re-login and now names the likely cause; a `409` on an element delete is a transient release race
that a plain retry clears, not the undeletable element it had been characterized as; and the
configuration-export `406` is not a vRA 8 trait but what every vRO tested answers. Alongside those: external
vRO appliances via `VCFA_VRO_HOST`, target guards on `create-deployment` — the one tool in the surface that
provisions infrastructure — `force` on the three vRO element deletes, and an end to redirect-following on
JSON requests. No tools were added; the surface stays at 78.

### Added

- `create-deployment` takes `expectedCatalogItemName` and `expectedProjectName`, verified against live metadata before the request is submitted, and is annotated destructive. It is the one tool in the surface that *provisions* infrastructure, and it had only the `confirm` flag: both of its required arguments are opaque UUIDs that nothing else in the call identifies, so a transposed one requested a different blueprint into a different project and the tool reported success. Its siblings `delete-deployment` and `run-deployment-action` already re-read the live object first; this brings the provisioning path into the same two-phase flow. Only the *names* are offered: an expected ID would compare an argument of this very call against itself and could never fail, which is worse than no guard because it looks like verification — the distinction from `delete-deployment`'s `expectedProjectId`, which checks a property of a live deployment the caller never typed. Each read fires only when the matching argument is supplied, so a caller passing neither pays exactly what it paid before, and the reads stay behind the `confirm` gate, which still refuses before any HTTP. Both names are optional on the wire, so an absent one is reported as "cannot verify" rather than as a mismatch against `(missing)` — the VCFO-077 resolution, which was a real defect where supplying an argument refused every call on a platform that omits the field — and a verification read that fails outright says so rather than surfacing as `Failed to create deployment`, which would leave an operator unable to tell whether anything was provisioned. The destructive annotation is a deliberate exception to the convention that additive `create-*` tools are excluded, recorded at both the annotation and the test that enforces it: provisioning is strictly neither an overwrite nor a delete, but `destructiveHint` is a host-side elevated-approval gate and allocating billable compute, storage and address space is what that gate exists for, while the premise behind the exclusion — that a delete restores the prior state exactly — does not hold when the removal path is itself destructive. The unconfirmed prompt now states the provisioning impact, and says when the target IDs will not be verified. `vra8` behaviour is unchanged: the catalog-service request is still refused, after the expected-field GETs. Verified by unit tests only; the live exercise needs a tenant session on a 9.x lab and is tracked under VCFO-074 (VCFO-084).

- `delete-workflow`, `delete-action` and `delete-configuration` take an optional `force`, which sends vRO's own `?force=true` — the documented way to remove an element vRO reports as in use. It sits behind the existing `confirm` gate and the `expected*` target guards, carries the destructive annotation like every other delete, and defaults to `false`, so an ordinary delete still issues the bare request. When it is set, the unconfirmed prompt says so before anything is sent: `force` skips vRO's reference check rather than establishing that nothing references the element, which is exactly the impact the two-phase flow exists to state. It is deliberately documented as the *second* step behind a plain retry — see the `409` entry below for why. Verified live on the `/workflows` route; `/actions/{id}` and `/configurations/{id}` are wired identically but never produced a `409` to test against, and the verification matrix records that gap (VCFO-087).

- The default `vcfa` platform has a per-tool verification record: `docs/operations/vcfa-verification-matrix.md`, from a full-surface live sweep of all 78 registered tools against VCF Automation 9.1 with the appliance-embedded vRO 9.1.0 (204 calls, provider session, environment returned to its exact starting counts). It replaces the situation where the *non-default* `vra8` matrix was the only per-tool evidence in the repo and could be misread as 9.x evidence; both matrices now cross-link and state which platform they attest to. The sweep measured vRO 9.1 list semantics directly rather than inheriting them from vRA 8, and they differ: `/workflows` applies `conditions` server-side and case-insensitively and honors `maxResult`, but ignores `startIndex` and answers `queryCount=true` with a `400`, so an unfiltered listing trips the repeated-page guard and the category traversal is the normal path there, while `/actions`, `/packages`, `/configurations` and `/resources` ignore `conditions` and `maxResult` entirely — which is what makes the VCFO-073 client-side post-filter load-bearing on 9.1 too. VCFO-060 is confirmed on 9.1: a scaffolded artifact with four input types imported, opened and ran, returning its declared output. VCFO-074, VCFO-076, VCFO-077, VCFO-080 and VCFO-085 are each confirmed on 9.1 rather than carried over, the last by observing the refusals themselves — project-service `403`, the other five `500`. All three API-version modes were exercised: unset auto-probes to `9.1.0`, and `vcfa9.1` and `vcfa9.0` pin and skip discovery; this evidences the `vcfa9.0` pin mechanism only, so that platform stays generalized rather than verified. The safety surface holds — 32 of 34 `confirm` gates refuse before any HTTP, the two exceptions (`update-configuration`, `ensure-project-package`) taking one deliberate non-mutating read first so the prompt can name the target — and no password or bearer token appeared in 227 captured results. The split-host `VCFA_VRO_HOST` topology was not exercised and the 20 tenant-scoped Automation tools remain blocked by the provider identity; both are recorded as open (VCFO-086).

- `VCFA_VRO_HOST` points the vRO `/vco/api` requests at an external vRO appliance while the login, the `GET /api/versions` probe, and the five Automation services stay on `VCFA_HOST`, on `vcfa`, `vcfa9.x`, and `vra8` alike. No second login runs: the token the Automation appliance issues is accepted verbatim by the external vRO, verified live on VCF Automation 9.1 with an external vRO 9.1 (the vRA 8 topology is wired identically but not yet live-verified). Unset, blank, or equal to `VCFA_HOST`, nothing changes. While the two hosts differ, every `[vro-client]` log line and every `vRO API error` ends with ` on <host>`, so a `403` with an HTML body — the Automation appliance's embedded orchestrator refusing a tenant whose organization uses an external vRO — is attributable at a glance; with the variable unset, that same `403` on a `/vco/api` request now carries a hint naming the variable, and no longer costs a re-login and a retry first — an HTML refusal is the appliance turning the tenant away, which a fresh token cannot change. The hint is limited to `/vco/api`, the only thing the variable moves, so an HTML `403` from the catalog, deployment, blueprint, or project service does not point at it. The server logs the routing once at startup (VCFO-081).

### Changed

- Configuration writes send the plural `attributes` key on every platform; the per-platform branch is gone. `vcfa` mode had always sent the singular `attribute` simply because the plural form had never been tried there, while vRA 8 requires the plural one and answers `400` for a body carrying the singular key at all — including one carrying both, so no single body could satisfy both platforms. VCFA 9.1 accepts the plural key on `POST /configurations` and on `PUT /configurations/{id}` alike, with the stored values confirmed by reading the element back rather than inferred from a `2xx`, so one key now serves every platform and the response shape, which was already plural everywhere, stops disagreeing with the request. The `vcfa9.0` pin is generalized to rather than verified: no 9.0 environment was available, and a 9.0 that rejected the key would fail loudly on create and update rather than silently storing nothing (VCFO-074).

- JSON API requests no longer follow redirects. Fetch strips `Authorization` on a cross-origin redirect, so a followed `302` could only ever reach a UI or SSO page unauthenticated, and it then surfaced as a `200` HTML body failing JSON parsing with no host named; the `3xx` is now reported with its status, the redirect target's host (never its query), and the variable to check. The binary-export and multipart-import paths keep fetch's default, so a same-origin redirect they relied on before is still followed. Transport failures name the host they were addressed to — `Request to vro.example.com failed: ENOTFOUND` rather than a bare `fetch failed` — with the original error kept as `cause`, and a connection that drops partway through a response body is reported the same way instead of as a bare `terminated`. A request that trips its deadline is reported as `Request to <host> timed out after <N> ms` rather than as undici's bare `AbortError`; only a deadline-bearing call can report it, since a body read runs after the deadline is cleared and an abort there stays a plain failure. Both `VCFA_HOST` and `VCFA_VRO_HOST` are trimmed, and a value that cannot serve as the host of a URL is rejected at startup with an actionable message: a URL scheme for either (`https://host` could never have connected), a path for `VCFA_VRO_HOST`, and a value such as `foo:bar` or a bare `::1` for both, which would otherwise have failed later as an opaque `Invalid URL` (VCFO-081).

### Fixed

- A `409` on a workflow, action, or configuration delete now explains itself instead of surfacing as a bare conflict. vRO's own body names a remedy — `Specify '?force=true' parameter to delete it` — that an MCP caller has no way to send, so the error carries a hint re-spelling it as the `force` argument. The hint leads with a **retry**, not with `force`, because a live re-run contradicted the premise this was filed under: the refusal is transient, not terminal. VCFO-086 recorded it as an element orphaned by `delete-package` with `deleteContents: false` becoming permanently undeletable, and the sweep's teardown reached outside the server twice to clear one. Re-measured on VCF Automation 9.1 with the appliance-embedded vRO 9.1.0, it is a release race: `delete-package` frees its members asynchronously, and for about two seconds afterwards the element still reports as in use. Four of eight immediate deletes answered `409`; none of four did after a five-second pause; in three of three timed samples a plain retry succeeded 2.2-2.3s after the first refusal. An element in a package that still exists never tripped it, nor did one never packaged, and nothing was ever permanently stuck. `force` stays the right tool for an element that is genuinely referenced, but reaching for it to clear a refusal a retry would have cleared skips a reference check that was doing real work — so the hint, the tool descriptions, and `AGENTS.md` all put the retry first. vRO's own sentence is kept rather than replaced, unlike the `406` refusal above, because it identifies the element. The hint is suppressed when `force` was already set (VCFO-087).

- A `403` on the default `vcfa` platform no longer costs a pointless re-login and retry. Any non-HTML `403` was treated as a stale session, on an assumption carried since VCFO-038; measured against a VCF Automation 9.1 appliance it is wrong — a revoked session answers `401` (`The token is not valid or revoked.`), an absent or malformed token answers `401` on `/vco/api` and on all five Automation services, and every observed `403` was a genuine denial. A `403` is now surfaced immediately, so a vRO permission refusal or a tenant-scoping refusal costs one request instead of two plus a login. `401` refresh is unchanged, and `vra8` keeps its challenge-gated rule. The `WWW-Authenticate` challenge is deliberately not used as the `vcfa` discriminator: project-service sends one on a `403` that is a real denial, while `/vco/api` and the catalog, deployment and blueprint services omit it even on a `401`. (VCFO-083, VCFO-085)
- A `403` or `500` from one of the Automation services now says what to do about it. Those services are tenant-scoped, so a provider (`VCFA_ORGANIZATION=system`) session cannot read them — project-service answers `403` and the catalog, deployment, blueprint and event-broker services answer `500` — while vRO answers normally on the same session. The error now carries a hint naming `VCFA_ORGANIZATION` on a provider session, and on any other session a `403` points at the user's roles rather than their credentials — on both platforms, since `vra8` reaches the same services and had been answering an Automation-service `403` by sending the operator to audit vRO permissions. The server-error arm is that one status rather than the `5xx` range: `502`, `503` and `504` come from whatever fronts the service and mean it is down, so they carry no hint. A `vcfa` `403` from vRO gained the same authorization-not-authentication hint `vra8` already had. (VCFO-085)
- `get-project` prints the role assignments VCF Automation 9.x actually serves. The project-service object differs by platform, and only `administrators` is common to both: vRA 8 serves `members`/`viewers`/`supervisors`, while 9.1 serves `advancedUsers`/`users`/`auditors`. The one 9.1 project available was auto-created with every role array empty and carried none of `constraints`, `properties`, `operationTimeout` or `sharedResources`, which is what that response held rather than proof 9.x never serves them; the type is a union either way, so the renderer prints whichever fields arrive. The `Project` type had been extended from a vRA 8 lab alone, so on 9.x three of the four role arrays were dropped silently and a project rendered as name, ID, description, organization ID and `Administrators: none` — the renderer omitting absent sections is what made the gap invisible rather than an error. All three are now declared and rendered; the vRA 8 output is byte-for-byte unchanged. The renderer no longer works from a fixed list of names at all: the known arrays print first, in a fixed order that does not follow the key order the service happens to serve, and any further array of principal-shaped entries prints after them under a humanized form of its own key — so the next platform to add a role does not repeat the silent drop. An unknown array that arrives *empty* is still skipped, because there is no entry to recognize it by; that costs at most a `none` line for a role nobody holds. The tool description names both platforms' role arrays rather than only the vRA 8 ones, matching what the docs already said. `Project.name` is optional like `CatalogItem.name`, so a row served without one renders as `(unnamed)` rather than as `undefined` — the convention, not an observed gap: every project on both labs carried a name. The rest of the endpoint is confirmed rather than changed: the path, the Spring page envelope, `page`/`size` (a second slice reports `number: 1`, so the repeated-page failure the issue was opened for cannot arise), the default `size` of 500, get-by-ID, the `404` for an unknown ID, and the project ID's acceptance by the blueprint and deployment services all match the vRA 8 behaviour. The `$filter` fallback now also triggers on the `500` both project-services answer for an element of the filter expression they do not know, rather than on a `400` alone, and logs the status that triggered it — a platform rejecting `substringof` or `tolower` the way the known ones reject an unknown field reaches the client-side match instead of surfacing as an error. Other statuses still surface, and `401`/`403` continue to reach the re-authentication path first. The VCFO-072 `$filter` is accepted **and applied** on 9.1 — asked for a needle matching nothing it returns an empty page, not the full inventory — `substringof` is case-sensitive there too, and description matching is confirmed on 9.1, which the vRA 8 lab could not show because its only project had an empty description. Verified on a tenant session: a provider (`system`) session cannot read the Automation services at all on 9.1 — project-service answers `403` with an empty body and the catalog, deployment, blueprint and event-broker services answer `500`, one of them naming a refused `rbac-service/api/auth-context` call as the cause — so those services are tenant-scoped and the provider half of the check has no target. 9.0 remains generalized rather than verified: no 9.0 environment was available, and the request carries no API-version element to pin (VCFO-065).
- `list-catalog-items`, `get-catalog-item`, `list-deployments` and `get-deployment` render a row served without a name as `(unnamed)` instead of `• undefined (id: …)`. `CatalogItem.name` and `Deployment.name` are now optional, matching `Subscription.name` — the same defect VCFO-070 found live, where 5 of 68 subscriptions carried no name at all. Neither shape had ever been seen: both verification labs had an empty catalog and no deployments, and the tool tests stubbed hand-written rows that would have passed regardless. A released catalog item has since been read on a VCFA 9.1 lab and renders correctly, which settles that shape on 9.x but not on vRA 8; no deployment has been observed on either platform. Every one of these guards tests truthiness rather than nullishness, in the subscription and project tools as well, so a row or a role principal carrying an empty-string name renders as `(unnamed)` instead of as a blank (VCFO-074).
- A `406` on a configuration-element export is reported as the actionable refusal — what the server declined and the project-package route that works — rather than as the server's HTML error page, which carries no diagnostic detail. The pre-emptive `vra8` guard is unchanged; this covers every other platform, because a standalone vRO 9.1 turns out to refuse the same request the same way: `application/zip`, `application/vcoobject+zip` and `application/octet-stream` all answer `406`, while `*/*` returns the element as JSON. Workflow, action and package exports answer `200 application/zip` on those same hosts in the same session, so the refusal is specific to configuration elements rather than to the host or the identity, and the behaviour documented as a vRA 8 trait is not specific to vRA 8. No vRO tested serves a `.vsoconf` for a single element, which leaves `import-configuration-file` with no genuine container to be fed from any environment — the route this issue expected a 9.x lab to open. The message states only what the server answered (VCFO-074).
- The `vcfa` session `POST` no longer follows redirects. A `VCFA_HOST` that answers `/cloudapi/1.0.0/sessions` with a redirect — an external vRO appliance does exactly this, as do SSO portals and some load balancers — used to have the redirect followed to an HTML page that passed as a `200`, so the failure surfaced as `VCF authentication succeeded but x-vmware-vcloud-access-token header was missing`: nothing had succeeded, and no host was named. The credentials ride in the Basic `Authorization` header, which fetch strips on a cross-origin redirect, so a followed redirect could only ever reach the SSO or UI page unauthenticated. The `3xx` is now reported with its status, the redirect target's host (never its query), and the variable to check, matching the JSON API path. A `2xx` that genuinely carries no token header — a host serving an SSO page instead of redirecting to one — now names the status and the declared content type rather than claiming success, and still never echoes the body, which on a login `2xx` can carry token material. Other non-`2xx` login failures are unchanged, including the `401` organization and provider hints, except that a response whose body could not be read is now reported as such instead of as an empty one. The `GET /api/versions` probe keeps fetch's redirect default: it carries no credentials, and against a redirecting host it already degrades to a warning and the `9.0.0` fallback before the session `POST` reports the redirect (VCFO-082).
- `get-configuration` prints attribute values instead of the raw vRO value envelope: `setting (string): "probe-2"` rather than `setting (string): {"string":{"value":"probe-2"}}`. Unwrapping is structural and shares the encoder's type-key mapping, so it follows the envelope rather than the declared type — vRO answers a `Date` attribute under the lowercase `date` key — and it covers arrays (`["one"]`), properties, and SDK-object descriptors as well as scalars; an envelope it does not recognize still renders raw rather than being guessed at. A value that is genuinely `""`, `0` or `false` now renders as that value: "no value" is decided on the envelope being absent, which is the case the built-in `BatchAction` element's valueless `Array/Action` attributes exercise. Secure attributes stay `[redacted]`, and an attribute whose declared type is permissive but whose value arrives in a `secure-string` envelope is redacted too. The same unwrap now serves `get-workflow-execution` and `run-workflow-and-wait`, replacing a narrower helper there that leaked the raw envelope for array outputs. The envelope shapes were read off a live vRO 8.18.1 configuration element; `Properties` is covered from the encoder instead, because a `Properties` attribute cannot currently be authored through the configuration tools (VCFO-080).

## 3.1.0 - 2026-09-11

The first release since 3.0.0. `VCFA_TARGET_PLATFORM=vra8` moves from a login-only mode to a
lab-verified surface: the whole vRO `/vco/api` surface, the Automation-service reads, and the
blueprint and event-broker writes are supported, each verified against a vRA 8.18 lab rather than
assumed. All 78 registered tools were then driven through the real tool handlers against that lab in
one pass, which found and fixed four defects and is recorded per tool in
`docs/operations/vra8-verification-matrix.md`. The flat `list-*` tools also gain an opt-in `limit`.

### Added

- **The whole `vra8` surface was driven through the real tool handlers against a vRA 8.18 lab** — all 78 registered tools, 277 captured calls, with the environment returned to its exact starting counts afterwards. Results are recorded per tool in `docs/operations/vra8-verification-matrix.md`, and the `vra8` section of `docs/operations/live-smoke-tests.md` now covers the action, resource, direct-package and project-package chains, the discovery and promotion tools, and the live-vs-file diff modes it was previously silent on. The sweep settled three open questions: a scaffolded `.workflow` — nine input types, a scriptable task and a native action item — imports, opens and **runs** on vRO 8.18.1, so the VCFO-060 container fix holds beyond the vRO 9.1 environment it was verified on; the VCFO-073 client-side post-filter and the VCFO-072 project `$filter` both behave as intended live; and `import-configuration-file` cannot be settled on vRA 8 at all, because a project-package export stores elements as `elements/<id>/data` rather than as `.vsoconf` members, leaving no container to feed back (VCFO-075).

- **`VCFA_TARGET_PLATFORM=vra8` now supports the blueprint-service and event-broker writes.** `create-template`, `delete-template`, `create-subscription`, `update-subscription`, and `delete-subscription` were verified against a vRA 8.18 lab with a disposable DRAFT template and a disposable disabled, non-blocking subscription — neither provisions infrastructure — and the guard is now per service rather than one message for four. Catalog-service and deployment-service writes (`create-deployment`, `delete-deployment`, `run-deployment-action`) still refuse, and each refusal now names what verifying that service would take: released catalog content for the request path, an existing deployment for the delete and day-2 paths. The service map is exhaustive, so adding an Automation service forces a supported/withheld decision instead of defaulting to permitted (VCFO-070).

- All 13 flat inventory tools accept an optional `limit` (1–1000): workflows, actions, configurations, categories, resource elements, packages, plugins, catalog items, projects, deployments, templates, event topics and subscriptions. Both pagers stop after enough matches and clamp request sizes when no client-side filter is active; local action/plugin filters and the project search fallback count matches before limiting. Category-scoped configurations slice after relation filtering, and the workflow category fallback preserves its full traversal, deduplication and global sorting. Snapshot and promotion callers remain unlimited (VCFO-064).

- **`VCFA_TARGET_PLATFORM=vra8` now supports the full vRO `/vco/api` surface and the Automation-service read paths.** Both were verified against a vRA 8.18 lab (vRO 8.18.1): creating, updating, and deleting workflows, actions, and configuration elements; the multipart artifact imports; package build, export, and import; and the list and get paths of the catalog, deployment, blueprint, project, and event-broker services, which return the same page envelope and object shapes the VCFA 9.x clients already parse. The flat guard that rejected every non-`/vco/api` base URL and every vRO write other than `POST /workflows/{id}/executions` is now a per-service, per-method one. No `apiVersion` pin turned out to be needed: none of the Automation-service clients sends one, and every endpoint answered without it — closing that open question from VCFO-063's scope. `shouldReauthenticate` and the `403` hint added in VCFO-067 were confirmed correct rather than changed: an invalid or expired token answers `401` with a `WWW-Authenticate: Bearer` challenge, on `/vco/api` and on the Automation services alike, while a genuine authorization denial answers `403` with no challenge (VCFO-068).

- `VCFA_TARGET_PLATFORM=vra8` now authenticates against vRA 8 (embedded vRO) with the platform's bearer-token flow instead of HTTP Basic: the client posts the configured credentials to `POST /csp/gateway/am/api/login?access_token`, sending `VCFA_ORGANIZATION` as the vIDM `domain` (for example `System Domain`), exchanges the returned `refresh_token` at `POST /iaas/api/login`, and sends the resulting token as `Authorization: Bearer` on every `/vco/api` request. Real vRA 8.18 appliances reject Basic auth on `/vco/api` with `401` and `WWW-Authenticate: Bearer`, so the previous mode could not log in at all. Login failures carry a hint that `VCFA_USERNAME`/`VCFA_PASSWORD` are vIDM credentials and `VCFA_ORGANIZATION` is the vIDM domain; tokens, refresh tokens, and passwords are never logged or surfaced, and 2xx login bodies are never echoed into errors (VCFO-067).

### Changed

- `list-projects` sends its search to the server. The optional `search` is now an OData `$filter` on `GET /project-service/api/projects` — `substringof('<search>', tolower(name)) or substringof('<search>', tolower(description))`, with the search trimmed and lower-cased and single quotes doubled — instead of a client-side substring match applied after every page had been collected. `totalElements` and the truncation flag therefore describe the matches, and a narrower search reaches projects beyond the pagination cap, so the tool uses the shared "narrow the query with a filter" truncation note and its project-specific note, along with the `scannedElements` / `inventoryTotalElements` fields on `ProjectList`, is gone. The filter shape was lab-verified on vRA 8.18 in `vra8` mode, where plain `substringof` is case-sensitive and `tolower()` makes it case-insensitive; VCFA 9.x has not been probed for `$filter` support yet, so a service that answers the filtered request with `400` falls back to the previous client-side match on the full list and logs that on stderr. `VroHttpClient.apiError` now attaches the HTTP status to the error it builds, readable through the new `apiErrorStatus` helper, so the fallback keys on the status rather than on the message text (VCFO-072).
- `get-project` renders the whole project-service object instead of only name, ID, and description: organization ID, shared-resources flag, operation timeout, machine naming template and placement policy (lifted from the `__namingTemplate` and `__projectPlacementPolicy` properties), custom properties with credential-looking keys shown as `[redacted]`, the administrators, members, viewers, and supervisors, and a per-kind count of placement constraints; sections the response does not carry are omitted. The field set was read off a vRA 8.18 lab, which also confirmed the `GET /project-service/api/projects` path, the Spring page envelope (`content`, `totalElements`, `totalPages`, `last`, default `size` 500), that `page`/`size` are honored (`page=1&size=2` answers `number: 1, first: false`), that an unknown ID surfaces as `404 Not Found` in `Failed to get project:`, and that the returned `id` is the `projectId` the blueprint and deployment services accept. Cloud zones are not part of this view. `list-projects` and `get-project` needed no path or pager change; the VCFA 9.x and tenant-session checks from the issue remain open (VCFO-065).
- `update-configuration` now runs its two-phase flow in the intended order. The live element is read once, before the `confirm` gate, and serves the `expectedName` guard, the safety check, and the update itself, so a guarded update costs one `GET` instead of two and a call that cannot succeed is refused before confirmation is spent. The `confirm: false` response names the element and the fields that will change. The refusal for an omitted attribute set now says which of the attributes are secure and that their values must be supplied fresh, because `get-configuration` prints them as `[redacted]`; and a secure-typed attribute supplied without a value is refused rather than stored as an empty secret (VCFO-071).
- The vra8 `403` authorization hint has one owner. `VroHttpClient.apiError(res, label)` builds every `vRO API error` message — status and reason, operation label, sanitized body, platform hint — for the JSON path and for the eleven binary-export and multipart-import sites in the artifact clients that used to assemble the same template by hand, and the hint's predicate is now the negation of `shouldReauthenticate` instead of a second copy of the same three clauses. `apiErrorHint` is private (VCFO-071).
- Error messages fall back to the standard reason phrase when a response carries none. Responses over HTTP/2 have no reason phrase, so `Response.statusText` is empty there and a message used to read `vRO API error: 400  — POST /configurations`; it now reads `400 Bad Request` (VCFO-071).
- The vra8 operation gate is private to the JSON request path and keys on method and base URL only. After VCFO-068 lifted every vRO restriction, the thirteen explicit `assertOperationSupported` calls in the artifact clients could no longer throw, its `path` parameter was unused, and the unknown-service branch was unreachable because every Automation client passes one of the five public base URLs verbatim; all three are gone (VCFO-071).
- Every client-side list filter (`list-projects`, `list-actions`, `list-configurations`, `list-workflows`, and `list-plugins` in `vra8` mode) shares one normalization: the filter is trimmed and lower-cased, and a blank filter is treated as absent. Previously two of the five trimmed and three did not, so `" Library"` matched plugins and projects but no actions (VCFO-071).
- Enabled Dependabot security updates on the repository, so transitive advisories now get their own pull requests instead of waiting for the monthly grouped version updates (VCFO-066).
- `vra8` mode now participates in the invalidate-token, re-authenticate, retry-once handling on `401`, because the CSP/IaaS bearer token expires. Previously `vra8` treated a `401` as terminal because Basic credentials cannot expire. The refresh token from the CSP login is kept, so a renewal replays only the `/iaas/api/login` exchange — one round trip, and the password does not go over the wire again — and the full CSP login runs only when that refresh token is rejected (VCFO-067).
- A `401`/`403` retry now invalidates only the token the failed request actually used. Previously the cached token was cleared unconditionally, so when several requests were in flight as a token expired, each stale `401` threw away a token a concurrent request had just obtained and forced another full login; in `vra8` mode that cost two round trips and a password resend per request (VCFO-067).
- In `vra8` mode a `403` from `/vco/api` is retried only when it carries a `WWW-Authenticate` challenge. An expired vRA 8 token answers with `401`, whereas a `403` there means the vIDM user lacks the vRO permission, so the previous behavior spent a full re-login and a retry that was certain to fail the same way. Such a `403` is now surfaced immediately with a hint that the login succeeded and the problem is authorization; the hint is appended on the JSON path and on the binary-export and multipart-import paths, which build their own error messages. The `vcfa` platform still retries both statuses. The vRA 8 status semantics behind this were subsequently confirmed in the lab under VCFO-068 (VCFO-067).
- The two `vra8` login POSTs no longer follow redirects. Their body carries the cleartext password and a `307`/`308` preserves the body across origins (the Fetch standard strips an `Authorization` header on a cross-origin redirect, but nothing strips a body), while a `302`/`303` would quietly turn the POST into a GET of an SSO page answering `200` with HTML. A redirect is now reported as a login failure naming the host it points at, with no credential material and no redirect query echoed (VCFO-067).
- `VCFA_ORGANIZATION` is trimmed before it is sent as the vIDM `domain`, matching the trim the provider-login check has always applied. A trailing space or `CR` — easy to acquire in a value that legitimately contains a space, such as `System Domain` — previously reached the CSP login and came back as an opaque `400` on a domain that looked correct (VCFO-067).
- `VroHttpClient` builds credential material for the active platform only. The `vcfa` session Basic header and the `vra8` CSP login body were both constructed for every client, so the default platform retained a cleartext copy of the password it never previously held, and `vra8` mode carried a dead Basic header plus a provider-session URL derived from the vIDM domain. `ensureAuthenticated()` is now private; `authorizationHeader()` is the only auth entry point, and it is what changed meaning for `vra8` in this release — it returns `Bearer <token>` where the method behind it used to return a complete `Basic …` header (VCFO-067).
- The `vra8` unsupported-operation message no longer describes the mode as "Basic-auth mode" (VCFO-067).
- Automation-service **writes** are what `vra8` mode now withholds, and the message says so: catalog item requests, deployment deletion and day-2 actions, blueprint create/delete, and subscription create/update/delete each provision or destroy real infrastructure, so they were left unexercised in the lab and still throw, while the reads alongside them go through. `export-configuration-file` is refused separately and for a settled reason rather than a pending one: vRA 8 serves a configuration element as JSON only and answers an artifact request with `406`, where the same request for a workflow or an action returns the artifact. That message points at `get-configuration` and the project-package route, both of which work (VCFO-068).

### Fixed

- **`export-action-file` and `diff-action-file` failed with an opaque `400` when given an action's fully qualified name.** vRO serves `GET /actions/<module>/<actionName>` as JSON but answers the same path with an artifact `Accept` with `400 Bad Request` and an HTML body carrying no diagnostic detail, so the tools dead-ended on the id form `list-actions` renders as an action's primary label — while `get-action` accepted it. `exportActionBuffer` now resolves a reference to its element id before the artifact request, using the same `parseActionReference` predicate `getAction` uses — so export and diff accept every id form `get-action` does, including the dot-separated variant, and element ids (UUIDs or long hex strings, carrying neither separator) are never re-resolved. A reference that resolves to a definition with no element id is refused by name rather than interpolated into the path. Verified on vRO 8.18.1 in `vra8` mode (VCFO-076).
- **`expectedCategoryName` on `update-resource-element` and `delete-resource-element` refused every call in `vra8` mode.** vRO 8.18.1 answers `GET /resources` with only `description`, `id`, `name` and `version` per element, and `getResourceElement` resolves from that listing, so the live category was always `undefined` and the generic field guard reported every supplied value as a mismatch against `(missing)` — blocking a legitimate update or delete no matter what the caller passed. The absent datum is now reported as "cannot verify here", naming `list-resource-elements` as the way to confirm placement, and the call is still refused rather than let through: a caller who asked for two-phase verification must not be told the target was confirmed when it was not. `expectedName` is checked first so an unverifiable category cannot mask a genuine name mismatch, an empty or null category counts as absent rather than as a mismatch against `""`, and the message is scoped to the element checked rather than asserting a property of the whole environment. The checks key on the missing value rather than on `targetPlatform`, so they stay correct wherever the listing does carry a category. `docs/reference/tools.md` records the argument's platform-dependent behavior (VCFO-077).
- The workflow preflight warning for a `<param>` `<description>` child asserted that "vRO emits bare `<param/>` elements", which is false on vRO 8.x: 8.18.1 exports its own workflows with those children, so a pristine `export-workflow-file` round-trip warned on every input parameter. The warning now names the VCF 9.x editor constraint it is actually about and says the shape is expected on an unmodified vRA 8 export. The rule itself is unchanged (VCFO-078).

- **Subscription writes in `vra8` mode sent a request shape vRA 8 rejects**, which the Automation-write guard had been hiding. Three differences, all verified live: vRA 8 requires the client to choose the subscription id (a body without one answers `500 The given id must not be null`), it answers the create `201` with an empty body and the created element in the `Location` header, and it serves neither `PUT` nor `PATCH` on `/subscriptions/{id}` (both `405`). `create-subscription` now generates a UUID and re-reads the created element — without the re-read the tool rendered the empty `{}` a bodyless response parses to, printing `Name: undefined`. A read-back that fails returns the posted element rather than throwing, since the POST already resolved: reporting a failed create for a subscription that exists invites a retry under a fresh UUID and a second live subscription. `update-subscription` now reads the live element, lays the caller's changes over it, and upserts the whole body with a `POST`. That upsert replaces what it does not carry, so the body starts from the live element and strips only the fields the server owns (`orgId`, `ownerId`, `subscriberId`, `system`, `contextual`, `selfLink`) rather than rebuilding an allow-listed one: the element's own `type` and any field `Subscription` does not model carry forward instead of being cleared by an update that never mentioned them. Nothing on the server side catches such a gap — the `400 Property: eventTopicId must not be blank` that rejects a partial body only fires when `eventTopicId` is absent, which the merge always supplies. An element carrying no `eventTopicId` is refused before the write instead. The `vcfa` path is unchanged (VCFO-070).
- `update-subscription` now rejects a confirmed call that supplies no field to change, the way `update-action` and `update-configuration` do. In `vra8` mode the update is a full-element upsert rather than a partial `PUT`, so a no-op call is a live rewrite (VCFO-070).
- `list-subscriptions` rendered `• undefined (id: …)` for every subscription the platform serves without a name — 5 of the 68 in the verification lab. `Subscription.name` is now optional, matching what vRA 8 actually returns, and the list, detail, create, and update renderers print `(unnamed)`. The adjacent `runnable: N/A/N/A` is correct and unchanged: those entries are `SUBSCRIBABLE` service subscribers with no runnable (VCFO-070).

- `list-packages`, `list-categories`, `list-configurations` (without `categoryId`) and `list-resource-elements` no longer present an unfiltered inventory as matches. All four sent the name filter to vRO as `conditions=name~<filter>` and trusted the server to apply it, but the vRO embedded in vRA 8 ignores that query on these endpoints and answers with the full list — verified on a vRA 8.18.1 lab, where `/packages?conditions=name~amqp` returned all 25 packages and `/categories?conditions=name~Library` all 134 categories. The filter was therefore a silent no-op there, and since the `limit` added in VCFO-064 it produced unrelated rows under a "showing the first N of 134" notice. Each listing now matches names client-side as a case-insensitive substring, the way `list-actions` and `list-plugins` already did, counting matches during pagination so a limit windows matching rows, and reports `total` as the match count rather than the server's inventory count. `conditions` is still sent, so a server that honors it returns the same rows over a smaller payload; only the requested page size changes there, staying at the configured 100 instead of clamping to the limit. Listings called without a filter are unchanged (VCFO-073).
- Small workflow limits no longer return names that violate the requested filter when early stopping bypasses repeated-page detection. Such responses use the existing category fallback, preserving filtering, deduplication and sorting before limiting (VCFO-064).
- Client-side filters retain the configured raw page size regardless of the result limit. Sparse action/plugin searches and the project HTTP-400 search fallback no longer exhaust the request cap by fetching one raw row per request with `limit: 1` (VCFO-064).
- Limited listings no longer present lookahead counts as estimated inventory totals. Unknown partial matching totals are omitted, known totals are retained, and the item-limit notice is distinct from the page-request-cap warning, including empty capped searches. A limit not reached before the safety cap is not falsely reported as `limited` (VCFO-064).
- Negative server totals (`total: -1` / `totalElements: -1`) are treated as unknown instead of ending pagination after the first page. This correctness fix intentionally also changes omitted-limit discovery on affected endpoints; otherwise full-list defaults and output remain unchanged (VCFO-064).

- `update-configuration` no longer clears the description of an element it was not asked to change. `PUT /configurations/{id}` replaces the element, and the body carried the description only when the caller supplied one, so a name-only or attributes-only update wiped it on both platforms. The description is now carried forward from the live element like the name (VCFO-071).
- `prepare-artifact-promotion` for a configuration artifact with `backup.enabled` no longer fails outright in `vra8` mode. The backup export hit the `.vsoconf` refusal (vRA 8 serves a configuration element as JSON only) and the throw discarded the preflight report, the diff, and the import recommendation that had already been computed. The backup is now reported as skipped with a note pointing at `get-configuration` and the project package, the way the missing-target-ID cases already were (VCFO-071).
- A vra8 login failure whose body is neither JSON nor a gateway HTML page no longer echoes an excerpt of that body. Both login POSTs carry a secret in the request body — the password, then the refresh token — so a gateway that reflects a rejected payload would have put a credential prefix into the error and, on the renewal path, into the log. Such a body is now reported by size and declared content type only; JSON diagnostic fields and gateway HTML summaries still come through. The same applies to the `vcfa` session login (VCFO-071).
- `VCFA_ORGANIZATION` is trimmed once, in the `VroHttpClient` constructor, for every consumer. VCFO-067 trimmed it for the provider-login check and the vra8 vIDM domain, but the `vcfa` Basic header still carried the raw value, so a trailing space or CR in the tenant organization produced a `401` with a hint that the slug was wrong (VCFO-071).
- Configuration writes now send the attribute key the target platform accepts. vRA 8 requires the plural `attributes` on `POST /configurations` and `PUT /configurations/{id}` and answers `400` for a body carrying the singular `attribute` — including one carrying both keys, so no single body satisfies both platforms. `create-configuration` and `update-configuration` with attributes therefore failed outright in `vra8` mode. The `vcfa` path still sends the singular key it has always sent; whether VCFA 9.x also accepts the plural form is unverified, so unifying on one key waits for a 9.x lab check rather than being inferred from the response shape, which is plural on both (VCFO-068).
- `update-configuration` now carries the element name in the `PUT` body when the caller is not renaming. `PUT /configurations/{id}` replaces the element, and vRA 8 rejects a nameless body with `The configuration element name contains invalid characters (\, /).Name: null`, so any update that changed only the description or the attributes failed in `vra8` mode. The live name is read first, the way `update-action` already re-reads the current action before its `PUT`; a call that does pass a name is unaffected and issues no extra request (VCFO-068).
- `update-configuration` no longer deletes the attributes it was not asked to touch. The underlying `PUT /configurations/{id}` replaces the element, so an update that changed only the name or the description dropped every attribute — contradicting the tool's own contract that only the supplied fields change. Such a call is now refused before the write, naming the attributes that would have been lost by name and type; values are never echoed. They are not carried forward automatically because a `SecureString` attribute reads back as ciphertext with `isPlainText: false`, and replaying that value risks storing the ciphertext as the new secret. Pass the attributes to keep, or an empty array to clear them deliberately. The behavior was reachable on both platforms, but only surfaced now: in `vra8` mode the same call previously failed at the nameless-body `400` above (VCFO-068).
- A gateway HTML error body is now summarized instead of truncated. The vRA 8 gateway answers a rejected `/vco/api` request with a styled HTML page whose only diagnostic content is the status code and reason, several hundred bytes past a stylesheet, so the 200-character non-JSON excerpt was pure CSS: a real `400` read as `vRO API error: 400  — POST /configurations` with nothing usable after it. The reason phrase matters more than it looks here, because these responses arrive over HTTP/2, which carries none, leaving `Response.statusText` empty and the page the only place it survives. Such a body now renders as `[HTML body: 400 Bad Request — no further detail]`, lifting out only the two short status fields and never echoing the surrounding markup; a page without them is reported as carrying no detail rather than quoted (VCFO-068).

- A `vra8` login that answered `2xx` without the expected field no longer misreports the cause. A body-read failure (a truncated connection) was swallowed and, like an HTML `200` from an SSO or proxy page, surfaced as "response did not include a refresh_token string. The login URL must keep the ?access_token query" — advice about an internal literal the user cannot change, with the real status and reason discarded. The message now names the status, the declared content type, and whether the body was unreadable, empty, non-JSON, or JSON without the field, and still never echoes a `2xx` body (VCFO-067).

- `list-plugins` no longer reports "No plugins found." against the vRO embedded in vRA 8 (`VCFA_TARGET_PLATFORM=vra8`). That server answers `GET /vco/api/plugins` with a flat `{ plugins: [...], total }` envelope instead of the `link`/`attributes` listing the other vRO list endpoints use, so the shared paginator saw zero items. The paginator now accepts endpoint-specific item keys and the plugin client reads both shapes, mapping the flat descriptor's `moduleName` (falling back to `id`), `version`, `description`, and `enabled` onto the existing plugin summary; a plugin the server reports as disabled is rendered with a `[disabled]` marker. `buildNumber`, `fileName`, and `logLevel` are not surfaced. Because that endpoint also ignores the `conditions` query (every name filter returned the full inventory), the `filter` argument is applied client-side to flat descriptors as a case-insensitive substring match on the module name, and the reported total then counts the matches; attribute listings keep the server-side filter (VCFO-069).

### Added

- **New read-only project discovery tools `list-projects` and `get-project`** backed by `GET /project-service/api/projects`, so agents can resolve the `projectId` consumed by `create-deployment`, `create-template`, `create-subscription`, and the project-scoped list tools instead of asking for it out-of-band. `list-projects` paginates the full project list and applies an optional client-side, case-insensitive name/description filter; when pagination hits the request cap, the result (even an empty match list) warns how much of the inventory was scanned and that the client-side search cannot recover the rest. ## 2.2.2 - 2026-06-24

### Fixed

- `import-action-file` now verifies `expectedCategoryName` against **live state**. Previously it compared the expected module name only against the caller-supplied `categoryName` (a tautology). It now also checks the live module set from `list-actions`, and when the target module does not yet exist the import proceeds and the result reports that a new module was created. Action modules are still discovered from the `module` column of `list-actions` (vRO does not expose them through `list-categories`) (VCFO-063).
- `run-workflow`/parameter marshaling now **rejects non-object `Properties` and `Composite` values** with a clear error instead of silently emitting a malformed `{ properties: { value } }` payload that the execution API would reject (VCFO-063).
- `get-workflow-execution` now renders output parameter values **unwrapped** (matching `run-workflow-and-wait`) instead of dumping the raw vRO type wrapper (for example `{"string":{"value":"x"}}`) (VCFO-063).
- `get-resource-element`/`getResourceElement` now **surfaces list truncation** instead of reporting a misleading "not found" when the live resource list was truncated at the page-request cap (VCFO-063).
- `list-workflows-by-category` now **surfaces category-list truncation** the same way: when the requested `categoryId`/`categoryPath` is absent and the live category list was truncated at the page-request cap, the error explains the category may exist beyond the returned page rather than asserting it does not exist (VCFO-063).
- `update-configuration` now rejects a confirmed **no-op** (none of `name`, `description`, or `attributes` supplied) before issuing a live update, matching `update-action` (VCFO-063).
- `getAllAutomationPages` now detects **non-advancing pagination** (a repeated page) and throws, matching the vRO pagination path, instead of silently looping to the page-request cap (VCFO-063). The repeat-detection signature was widened from a 32-bit to a ~53-bit hash so a false-positive "did not advance" at the page-request cap is negligible (VCFO-063).
- Category listings no longer assign `undefined` to the required `id`/`name` fields; they fall back to `""` consistent with the plugin client (VCFO-063).
- `parseAttrs` now skips attribute entries with a missing or non-string `name` so a malformed entry cannot pollute the parsed map (VCFO-063).
- The server now handles **`SIGTERM`** (in addition to `SIGINT`) so the transport and the HTTP dispatcher are torn down under process-manager termination; removed an unused import (VCFO-063).
- The `vcfa://context/snapshots/{fileName}` resource no longer advertises a misleading static `text/plain` mime type; the read handler reports the correct per-file `application/json` or `text/markdown` type (VCFO-063).

### Tests

- Added coverage for the action-import live module guard (existing/new/truncated module), non-object `Properties`/`Composite` rejection, `getResourceElement` truncation, `get-workflow-execution` output unwrapping, the `update-configuration` no-op guard, automation pagination non-advancement, the subscription OData single-quote escaping, the `resolveWorkflowCategoryFromList` truncation-aware not-found, and entry-point startup failures (missing env var and invalid `VCFA_TARGET_PLATFORM`) (VCFO-063).

## 2.2.1 - 2026-06-14

This release completes and hardens scaffolded-workflow support so generated `.workflow` artifacts import, open in the editor, and run in live vRO 9.1, and lets the scaffolder emit native vRO action workflow items.

### Added

- `scaffold-workflow-file` can emit **native vRO action workflow items** via an optional `kind: "action"` task discriminator (`module`, `actionName`, ordered `inputs`, `resultBinding`), generating the `actionResult = System.getModule("<module>").<actionName>(...)` script and a `type="task" script-module="<module>/<actionName>"` item; void actions omit `resultBinding` and emit a bare call. Tasks without `kind` behave exactly as before. `preflight-workflow-file` validates the `<module>/<actionName>` form and `diff-workflow-file` surfaces native-action item changes (VCFO-046, VCFO-059).

### Fixed

- Scaffolded `.workflow` artifacts now **import, open in the VCF 9.x Orchestrate editor, and run** in live vRO 9.1. The builder emits `workflow-info` as a Java properties file (not XML), encodes `workflow-content` as UTF-16BE with a `UTF-8` XML declaration (the BOM drives decoding; the v2 editor returns 500 on a declaration saying `UTF-16`), chains an explicit terminal `<workflow-item type="end">` (replacing `end-mode="1"` on the last task), writes `input_form_` only when the workflow has inputs, drops the read-only `allowed-operations` marker that made the editor refuse to open the workflow, and gives every item a distinct `<position>` with bare `<param>` elements (VCFO-060).
- `preflight-workflow-file` and `diff-workflow-file` now parse vRO's native repeated `<attrib name type read-only>` attribute shape (not just the scaffold's wrapped form), so scaffolds and real exports round-trip identically; binding type-match tolerates vRO's generic `Any`; and preflight parses `workflow-info` as properties, requires UTF-16BE content, and rejects the legacy `end-mode="1"` pattern (VCFO-061).

## 2.2.0 - 2026-06-12

This release adds VCF Automation 9.1 support with automatic API version negotiation, provider/system administrator logins, and fixes workflow and configuration parameter payloads to use the canonical vRO type keys the REST API expects.

### Added

- VCF Automation 9.1 support: the default `vcfa` platform now auto-negotiates the VCF Cloud API version before authenticating, probing the unauthenticated `GET /api/versions` discovery document and preferring `9.1.0` over `9.0.0`. A probe that fails outright falls back to `9.0.0` for that attempt only and discovery is retried on the next authentication; a probe that succeeds but advertises no known version caches the `9.0.0` fallback. Authentication is single-flighted, so concurrent requests share one probe and one session login. New `VCFA_TARGET_PLATFORM` values `vcfa9.1` and `vcfa9.0` pin the version explicitly and skip the probe (VCFO-057).
- Provider/system administrator logins: `VCFA_ORGANIZATION=system` (case-insensitive) now routes authentication to `/cloudapi/1.0.0/sessions/provider`; the tenant `/sessions` endpoint rejects provider accounts with 401. Login 401 errors now include a hint distinguishing organization names from display names and pointing provider accounts at `VCFA_ORGANIZATION=system` (VCFO-057).

### Fixed

- Workflow execution and configuration attribute payloads now key parameter values by the canonical lowercase/hyphenated vRO type literal (`secure-string`, `date`, `mime-attachment`, …) instead of the display type from the definition (`SecureString`), which the vRO REST API rejects with a 400. `Array/<type>` inputs are serialized as `{"array": {"elements": [...]}}`, SDK object types (e.g. `VC:VirtualMachine`) as `{"sdk-object": {"id", "type"}}`, and plain-object `Properties` values as `{"properties": {"property": [...]}}` (VCFO-058).
- `run-workflow` and `run-workflow-and-wait` input validation now rejects non-string values for `SecureString` and `EncryptedString` inputs instead of forwarding them to the vRO API (VCFO-058).

## 2.1.0 - 2026-06-12

This release scopes TLS relaxation to the client's own requests, hardens response parsing and artifact preflight, gates bulky tool output behind opt-in flags, adds two-phase confirmation fields for live mutations, and ships a Claude Code plugin with authoring and operations skills.

### Security

- `VCFA_IGNORE_TLS=true` no longer disables TLS certificate verification process-wide via `NODE_TLS_REJECT_UNAUTHORIZED`. TLS relaxation is now scoped to the client's own requests to the configured VCFA host through a dedicated HTTPS agent, so other HTTPS traffic in the same Node process keeps full certificate verification. The minimum supported Node.js version is now 18.17.
- `get-configuration` now redacts `SecureString` attribute values instead of returning them in plain text (VCFO-048).

### Added

- Added a Claude Code plugin (`vcfa-orchestrator`) and marketplace manifest under `.claude-plugin/`, bundling two skills in `skills/`: `vcfa-authoring` (discovery-first artifact lifecycle and package-first publishing) and `vcfa-operations` (running workflows and guided troubleshooting). The skills delegate to the server's existing `vcfa-*` prompts, resources, and tools rather than duplicating them, and `npm run validate:docs` now drift-checks the tool/prompt/resource names they reference.
- Added `VroClient.close()` to release the client's network resources (the TLS-relaxed dispatcher); the server now calls it during graceful shutdown.
- Added a local TLS integration test that runs the client against a self-signed HTTPS server, verifying `ignoreTls` completes a real handshake (and that strict mode still rejects) without touching `NODE_TLS_REJECT_UNAUTHORIZED`.
- Added optional two-phase confirmation fields to high-risk live mutation tools: when expected target fields such as `expectedName`, `expectedCategoryId`/`expectedCategoryName`, `expectedPackageName`, `expectedWorkflowName`/`expectedInputNames`, or `expectedDeploymentName`/`expectedActionName` are supplied, the handler performs read-only discovery first and refuses to mutate if the live target does not match. Omitted fields keep existing `confirm: true` behavior unchanged.
- Workflow tools now return `structuredContent` (structured workflow, execution, and execution-log shapes) alongside their text output.

### Changed

- `get-template`, `get-action`, and `get-subscription` now summarize bulky content (blueprint YAML, action script, constraints JSON) as a sha256 + length line by default, consistent with context-snapshot redaction; the new `includeContent`, `includeScript`, and `includeConstraints` flags restore the full output (VCFO-055).
- Tools that overwrite or delete live state — import, update, run, and delete tools, plus `rebuild-project-package` — now advertise `destructiveHint: true` in their MCP annotations so hosts can require heightened approval; additive creates and `add-*-to-project-package` tools do not (VCFO-051).

### Fixed

- `run-workflow` now validates and type-normalizes caller-supplied inputs through the same shared preamble as `run-workflow-and-wait` instead of POSTing them to the live workflow unvalidated; the two handlers' drifted input schemas (`inputs[].type` required in one, optional in the other) are reconciled (VCFO-047).
- Query parameter values containing `$` or `~` are no longer un-encoded by the pagination query serializer; the literal-`$` exemption now applies only to OData system query keys such as `$filter` and `$search` (VCFO-050).
- Empty-body 2xx responses with a `Location` header no longer masquerade as a running workflow execution for non-execution endpoints; the synthetic `{ id, state: "running" }` shape is now scoped to the explicit workflow-execution start path (`startExecution`), and generic empty 2xx responses return `{}` (VCFO-052).
- A 2xx response with a non-JSON body (for example an HTML error page from a load balancer or SSO interstitial) now throws a sanitized, contextualized error naming the method, path, and correlation ID instead of a bare `SyntaxError: Unexpected token` (VCFO-053).
- List results that stop at the pagination request cap now carry a `truncated` flag instead of silently returning partial data with the server's full total; list tools append a visible truncation warning and context snapshots record a per-domain warning (VCFO-054).
- Artifact preflight now rejects `input_form_` entries that are not UTF-16BE (the documented contract) instead of silently accepting UTF-16LE, decodes UTF-16 entries fatally so corrupt bytes fail instead of passing as U+FFFD mojibake, and reports XML-looking `.action`/`.vsoconf` archive entries with invalid byte sequences instead of skipping them (VCFO-056).
